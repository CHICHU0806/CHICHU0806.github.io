# 万事开头第一步

这是F407开发板系列教程中的第一份内容，也是我们脱离比较简单的元器件外设走向工业成品套件去玩转嵌入式开发的第一个教程。

而在正式进入底盘运动控制、云台控制以及后续其他进阶控制之前，我们首先需要解决一个非常朴素的问题：**如何让一个 M3508 电机真正转起来。**

对于 RoboMaster 电控方向来说，M3508 电机本身并不是直接接在单片机 IO 口上控制的，而是需要通过 C620 电调进行驱动；而 C620 电调与主控板之间最常用的通信方式正是 CAN 通信。因此，这一章的目标并不是一上来讲完整的 CAN 协议，而是先让大家通过大疆 C 板、C620 电调和 M3508 电机，完成一次最小可运行的 CAN 发送流程。

# 介绍下硬件资源

我们采用的是大疆官方 C 型开发板，也就是 DJI C Board，其主控芯片型号为 STM32F407IGH6。

本章使用的执行对象是大疆官方 M3508 电机与 C620 电调的组合，这一组合在 RoboMaster 队内训练和实际机器人底盘中都非常常见，所以非常适合作为 CAN 通信的入门对象。

在开始配置之前，我们先把几件事说清楚：

1. M3508 不能直接由 STM32 引脚驱动。

2. C620 电调接收 CAN 报文，并根据报文中的电流值驱动 M3508。

3. 大疆电调的经典 CAN 通信波特率一般固定为 1Mbps。

4. 对于初学阶段，我们先只做发送，不做反馈接收，也就是先实现开环转动。

为什么先做发送？因为如果连电流指令都不能正确发出去，那么后面所谓的速度闭环、位置闭环、电机反馈解析都无从谈起。所以这一章实际上是后续全部电机控制内容的地基。

# STM32CubeMX 的初步配置

在正式进入 CubeMX 配置之前，我们需要先明确一个事情：CubeMX 并不是一个需要我们从头到尾完全读懂的英文软件，它更像是一个芯片资源配置表。我们要做的不是翻译它里面的每一个选项，而是带着一个明确目标去告诉芯片：我要用哪个外设、用哪几个引脚、跑在什么频率下、是否需要中断或者 DMA，最后让它帮我们生成对应的初始化代码。

因此，刚开始学习 CubeMX 时不需要害怕界面复杂。对于我们目前的入门阶段来说，真正需要重点关注的部分其实只有 RCC、SYS、Clock Configuration、对应外设配置、NVIC/DMA 以及 Project Manager。只要能够理解这些区域分别负责什么，再结合具体任务一步一步配置，就已经足够完成绝大多数基础外设的初始化工作。

## 时钟树配置

首先让我们从时钟树开始。

通过查询大疆 C 板相关资料，我们可以知道这块板子的外部时钟输入频率为 12MHz。但是 CubeMX 默认情况下往往会优先使用 HSI，也就是 High Speed Internal，高速内部时钟。

内部时钟当然也能用，但是它的精度与稳定性一般不如外部晶振。对于 CAN 这种对波特率比较敏感的通信总线来说，时钟偏差会直接影响通信稳定性，所以我们一般会选择 HSE，也就是 High Speed External，高速外部时钟。

![image\.png](/images/posts/F407-Board/CAN/image5.png)

那么问题来了，外部晶振只有 12MHz，而 STM32F407 的最高主频可以达到 168MHz，我们显然不可能直接拿 12MHz 当系统主频使用。因此这里还需要引入 PLL，也就是锁相环（Phase\-Locked Loop）。

PLL 的作用可以类比变压器，能够将输入的频率进行“升压”，从而以高频输出，也就是：

```Plain Text
外部稳定时钟（相对低频）--倍频/分频--> 系统真正使用的高速主频
```

所以我们在时钟树中需要做的核心流程就是：

```Plain Text
HSE = 12MHz
HSE 作为 PLL 的输入
PLLCLK 作为 System Clock Mux
SYSCLK 拉到 168MHz
```

当我们把输入频率和系统主频设置好之后，CubeMX 一般会自动帮我们调整中间的倍频和分频参数。如果出现红色报错，就说明某一路总线频率超出了芯片允许范围，需要重新调整。

## RCC 配置

回到配置主页后，我们首先处理 RCC，也就是 Reset and Clock Control，复位与时钟控制模块。

这里我们需要启用高速外部时钟源，目的就是让前面时钟树中配置的 HSE 真正有来源。

![image\.png](/images/posts/F407-Board/CAN/image1.png)

这里不要把 RCC 当作一个无关紧要的配置项。如果外部时钟没有正确启用，那么后续你在时钟树里写得再漂亮，实际生成代码时也可能无法按照预期运行。

## SYS 配置

接下来是 SYS 配置。

首先需要设置 Debug 方式。对于大疆 C 板，我们使用 ST\-Link 进行调试和下载程序，因此这里选择 Serial Wire，也就是 SWD（Serial Wire Debug）。这个选项一定不要忘记，否则后续可能出现程序烧录后无法再次连接调试器的情况，也就是所谓的“成砖”，需要通过Boot引脚进行复原。

![image\.png](/images/posts/F407-Board/CAN/image7.png)

至于 Timebase Source，如果只是完成本章的 CAN 发送实验，使用 SysTick 或 TIM1 都可以完成基本功能。早期教程里我们选择 TIM1 作为时基，是因为 TIM1 是高级定时器，在电机控制相关内容中经常出现；但是如果后续工程中接入了其他内容，或者对延时函数有更高要求，就需要重新评估时基选择，避免不同模块之间出现冲突。

## CAN1 引脚配置

接下来我们正式进入 CAN 配置。

首先启用 CAN1。

![image\.png](/images/posts/F407-Board/CAN/image6.png)

这里有一个非常容易踩坑的地方：**CubeMX 自动给出的 CAN1 默认引脚不一定等于开发板实际接出来的 CAN 引脚。**

通过查询大疆 C 板原理图可以知道，C 板上的 CAN1 实际使用的是 PD0 / PD1，而不是默认状态下常见的 PB8 / PB9。因此我们需要在右侧引脚图中手动修改到正确位置。

![image\.png](/images/posts/F407-Board/CAN/image8.png)

![image\.png](/images/posts/F407-Board/CAN/image3.png)

这里需要注意的是，CAN 并不是普通 GPIO 高低电平通信。STM32 的 CAN\_TX / CAN\_RX 只是连接到板载 CAN 收发器的一侧，真正挂到 CAN\_H / CAN\_L 总线上的信号还要经过收发器转换。因此我们在 CubeMX 里配置的是芯片外设引脚，而在接线时需要接的是开发板对外引出的 CAN\_H、CAN\_L 和 GND。

# CAN 波特率配置

## 为什么必须是 1Mbps

下一步是 CAN 波特率配置。

由于大疆 C620 电调使用的经典 CAN 波特率为 1Mbps，所以我们在 CubeMX 中需要让 Baud Rate 最终等于或尽可能接近 1000000 bit/s。

![image\.png](/images/posts/F407-Board/CAN/image2.png)

如果这里配置成 500K、250K 或者其他频率，那么电调和主控板虽然都在发信号，但是彼此根本听不懂对方在说什么。这种问题在调试时很烦，因为你可能会怀疑接线、怀疑代码、怀疑电机，最后才发现只是波特率没对上。

## 波特率公式怎么理解

CubeMX 中的 CAN 波特率主要由三个参数决定：

1. Prescaler              预分频

2. Time Segment 1    时间相位1

3. Time Segment 2    时间相位2

经典 CAN 的波特率可以写成：

$BaudRate = \frac{1}{T_{bit}}=\frac{f_{CAN_{clk}}}{Prescaler \times (1 + TSEG1 + TSEG2)}$

在当前 168MHz 系统主频配置下，CAN1 挂载在 APB1 总线上，而 APB1 的频率一般为 42MHz。因此我们可以把公式理解为：

$1000000 = \frac{42000000}{Prescaler \times (1 + TSEG1 + TSEG2)}$

也就是说，**分母整体需要等于 42**。

一种比较常见且好用的配置是：

![image\.png](/images/posts/F407-Board/CAN/image.png)

```Plain Text
Prescaler = 2
TSEG1     = 15
TSEG2     = 5
SJW       = 1
```

此时有：

$2 \times (1 + 15 + 5) = 42$

最终波特率即为：

$\frac{42MHz}{42}=1MHz$



## **为什么还要看采样点?**

到这里可能会有同学觉得，只要能凑出 1Mbps 不就行了吗？为什么还要纠结 TSEG1 和 TSEG2 怎么分？

这里就需要引入一个概念，叫做**采样点 SP**。

这表示信息在总线传播时候的采样范围，在工业上这个值追求稳定度优先于极端采样点，常见建议把SP设在75%\~87\.5%范围，所以预分频极小或者TSEG2极端接近末尾都是不合理的。

CAN 总线上的一个 bit 并不是在整个时间段里随便读一次就行，而是会在某一个相对靠后的位置进行采样。这个采样点通常可以写成：

$SP = \frac{1 + TSEG1}{1 + TSEG1 + TSEG2}$

如果使用上面的配置，则有：

$SP = \frac{1 + 15}{1 + 15 + 5}=\frac{16}{21}≈76.19\%$

对于我们在队内使用的短距离电机 CAN 总线来说，这样的配置已经足够完成 M3508 的基础驱动。

至此，CubeMX 中 CAN1 的基础配置就已经完成。点击 Generate Code 之后，我们就可以进入代码层面的编写。

# 代码层面的发送逻辑

## CAN 报文到底要发什么

在这一小节中，我们只需要让电机转起来，而想要做到这一件事，从来都只需要向 C620 电调发送一段电流控制指令即可。

想要驱动任何一家公司出品的电机，第一件事便是去看他的控制协议：

![image\.png](/images/posts/F407-Board/CAN/image4.png)

对于大疆电机协议来说，一帧控制 1\~4 号电机电流的 CAN 报文，其标准 ID 为 0x200，数据长度为 8 个字节。其中每两个字节对应一个电机电流值，顺序如下：

```C++
Data[0] Data[1] -> ID 1 电机电流
Data[2] Data[3] -> ID 2 电机电流
Data[4] Data[5] -> ID 3 电机电流
Data[6] Data[7] -> ID 4 电机电流
```

那么我们不妨先把这件事转成更接近代码的语言：

1. 构造一个 CAN 帧头，告诉外设这帧报文发给谁、是什么类型、有多长。

2. 构造一个 8 字节数组，把 4 个电机的电流值依次塞进去。

3. 调用 HAL 库函数，把这段 CAN 报文送入发送邮箱。

4. CAN 外设从邮箱中取出报文，并真正发送到总线上。

## 为什么有帧头、数据和邮箱

在 F407 的经典 CAN 外设中，一次发送主要围绕三个东西展开：

```C++
CAN_TxHeaderTypeDef TxHeader;   // 帧头
uint8_t TxData[8];              // 数据区
uint32_t TxMailbox;             // 发送邮箱
```

这里的“帧头”的作用是描述这段 CAN 报文的基本属性。比如这段报文的标准 ID 是多少，是标准帧还是扩展帧，是数据帧还是远程帧，数据长度是多少。

而 TxData 则是真正要发出去的 8 个字节数据。对于本章的 M3508 控制来说，这 8 个字节里面装的就是 4 个电机的目标电流值。

最后的 TxMailbox 则是经典 CAN 中比较有代表性的概念。F407 的 CAN 外设不是你一调用函数就立刻把数据从引脚上喷出去，而是先把报文放进发送邮箱，之后再由硬件按照 CAN 总线规则完成仲裁和发送。

所以我们可以把整个发送过程理解为：

**软件构造报文 \-\> 塞进发送邮箱 \-\> CAN外设排队发送 \-\> C620电调接收解析**

# 发送函数的编写

当我们刚看到先前生成的CubeMX主框架，我们需要挑选一部分“安全区”才能进行我们主要内容的编写。我们可以选择的部分比如有`main.c`中的`/* USER CODE BEGIN 0 */`中提供的空余位置。

```C++
/* USER CODE BEGIN 0 */

                            ←------写在这里！

/* USER CODE END 0 */
```

```C++
HAL_StatusTypeDef CAN_Send_MotorCmd(int16_t motor1, int16_t motor2, int16_t motor3, int16_t motor4){
    //这里确定了我们想要发送的CAN帧的帧头，存储发送数据的数组以及发送所采用的邮箱名称
    CAN_TxHeaderTypeDef TxHeader;
    uint8_t TxData[8];
    uint32_t TxMailbox;
    
    //这里按照HAL库规定组装了帧头的四个元素
    TxHeader.StdId = 0x200;
    TxHeader.IDE=CAN_ID_STD;
    TxHeader.RTR= CAN_RTR_DATA;
    TxHeader.DLC=8;
    
    //这里用于拆分数据为高八位低八位进入预设数组以满足CAN帧规则
    TxData[0] = motor1 >> 8;
    TxData[1] = motor1;
    TxData[2] = motor2 >> 8;
    TxData[3] = motor2;
    TxData[4] = motor3 >> 8;
    TxData[5] = motor3;
    TxData[6] = motor4 >> 8;
    TxData[7] = motor4;
   
    //最后将我们确定的帧头，数组，邮箱等信息通过这一HAL库函数传递到hcan1来发送到总线上
    return HAL_CAN_AddTxMessage(&hcan1, &TxHeader, TxData, &TxMailbox);
}
```

这里我们逐步拆开来看。

首先是 `HAL_StatusTypeDef`，它是 HAL 库中非常常见的返回值类型，用来告诉我们这次 HAL 函数调用到底有没有成功。它大致包含 `HAL_OK`、`HAL_ERROR`、`HAL_BUSY`、`HAL_TIMEOUT` 这几种状态。

在 `stm32f4xx_hal_def.h` 中对这一枚举类型做了定义：

```C++
*/** *
*  * @brief  HAL Status structures definition  *
*  */  *
typedef enum 
{
  *HAL_OK       *= 0x00U,
  *HAL_ERROR    *= 0x01U,
  *HAL_BUSY     *= 0x02U,
  *HAL_TIMEOUT  *= 0x03U
} HAL_StatusTypeDef;
```

这也是为什么我们把发送函数写成带返回值的形式。因为一旦 CAN 发送失败，我们可以在主函数里根据返回值进入 `Error_Handler()`，从而更快定位问题。

接着看帧头部分：

```C
TxHeader.StdId = 0x200;
TxHeader.IDE = CAN_ID_STD;
TxHeader.RTR = CAN_RTR_DATA;
TxHeader.DLC = 8;
```

这几行其实就确定了这帧报文的身份：

```C++
0x200        -> 控制 1~4 号电机
CAN_ID_STD   -> 标准帧
CAN_RTR_DATA -> 数据帧
DLC = 8      -> 8 字节数据
```

然后是数据填充部分。虽然本章可能只接了一个电机，但是我们仍然一次性传入 4 个电机的电流值，这是因为 0x200 这帧报文本来就规定了 8 字节长度，每两个字节对应一个电机。

以 `motor1` 为例：

```C++
TxData[0] = (uint8_t)(motor1 >> 8);
TxData[1] = (uint8_t)(motor1);
```

这里的 `motor1` 是一个 `int16_t`，也就是 16 位数据，而 CAN 的数据区是按字节存放的，一个字节只有 8 位。因此我们需要把一个 16 位电流值拆成高 8 位和低 8 位分别发送。

这一步可以理解成：

```C++
int16_t motor1 = 高8位 + 低8位
TxData[0] 放高8位
TxData[1] 放低8位
```

如果这里高低位顺序写反，电调解析出来的电流值就会完全不对，所以这一块一定要按照电机协议来写。

# 在 main 函数中启动 CAN

定义好发送函数之后，我们还需要启动 CAN 外设。

在 `main.c` 的 `/* USER CODE BEGIN 2 */` 中加入：

```C
/* USER CODE END 2 */
HAL_CAN_Start(&hcan1)；
```

这里需要注意，CubeMX 生成了 CAN 初始化函数，不代表 CAN 外设已经开始工作。`MX_CAN1_Init()` 只是完成了基础配置，而 `HAL_CAN_Start(&hcan1)` 才是真正让 CAN 外设进入工作状态。

这一点也是我们以后经常需要使用的思路：

**先配置参数，再启动外设，最后进入循环使用。**

# 在 while 循环中发送电流指令

启动 CAN 之后，我们就可以在 `while(1)` 中周期性发送电流指令。

```C
/* Infinite loop */
/* USER CODE BEGIN WHILE */
while (1)
{
    if (CAN_Send_MotorCmd(1000, 0, 0, 0) != HAL_OK)
    {
        Error_Handler();
    }

    HAL_Delay(2);
    /* USER CODE END WHILE */

    /* USER CODE BEGIN 3 */
}
```

这样如果在CAN总线上出了什么差错都会直接进入错误中断，以便调试时检查问题。

这里的 `1000` 表示给 1 号电机发送一个较小的正向电流值，其他三个电机暂时给 0。

需要注意的是，这里不是发送一次就结束，而是要周期性发送。因为 C620 电调控制电机时希望持续收到控制帧，如果只发送一次，电机即使动一下也会很快停下来；在实际机器人控制中，我们通常会在固定控制周期内不断刷新电机电流指令。

调试初期建议从比较小的电流值开始，例如 `500`、`1000`，并且让电机离地测试，避免电机突然转动带来危险。

# 如果电机不转，应该先看哪里

到这里，理论上 M3508 已经能够转动。如果电机没有反应，不要一上来就怀疑代码全部写错，我们可以按照下面的顺序排查：

1. C620 电调是否供电正常，电机三相线是否接好。

2. CAN\_H、CAN\_L是否连接正确，是否存在 CAN\_H / CAN\_L 接反的问题。

3. CAN1 引脚是否确实改成了 PD0 / PD1，而不是停留在 CubeMX 默认引脚。

4. CAN 波特率是否为 1Mbps。

5. 是否调用了 `HAL_CAN_Start(&hcan1)`。

6. `HAL_CAN_AddTxMessage` 是否返回 `HAL_OK`。

7. 电机 ID 是否为 1，如果电机 ID 不是 1，那么 `0x200` 报文中的第一组电流就不会控制到它。

8. 是否周期性发送，而不是只发送了一次。

这里面最容易出问题的往往不是代码里的某一行，而是引脚、波特率、接线和电机 ID。嵌入式调试很重要的一点就是不要只盯着软件看，通信类问题永远要同时检查硬件链路和软件配置。

# 小结

现在让我们回过头看这一章真正完成了什么。

首先，我们知道了 M3508 并不是由单片机直接驱动，而是由 C620 电调接收 CAN 报文后完成驱动。

其次，我们完成了大疆 C 板上 CAN1 的 CubeMX 配置，包括 HSE 时钟、168MHz 系统主频、SWD 调试方式、CAN1 引脚重映射以及 1Mbps 波特率配置。

最后，我们在代码中构造了最基本的经典 CAN 发送帧，通过 `HAL_CAN_AddTxMessage` 将 0x200 控制报文放入发送邮箱，从而让 C620 电调接收到电流指令并驱动 M3508 转动。

本章只解决了一个问题：**如何把控制指令发出去。**

但是一台真正的机器人显然不能只靠开环电流控制。后续我们还需要继续学习如何接收 M3508 的反馈帧，如何配置 CAN 过滤器，如何解析转子角度、转速、电流和温度，并最终进入速度闭环和位置闭环控制。

至此，大疆 C 板的 CAN 通信入门部分就可以暂时告一段落。只要这个最小例子能够跑通，后面所有电机控制内容就都有了继续往下搭建的基础。
